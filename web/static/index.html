tiny-GPT-trainer — watching a run

A training run is worth watching. A scrolling log hides the two things most worth seeing: the shape of the loss curve, and the arc where a generated sample stops being noise and starts being language. This page shows both while they happen.

Each stage is one subprocess. The server shells out to the same python -m tinygpt.* commands you would type and reads their stdout, so the trainer needs no changes and does not know this page exists — and a run that crashes takes down a child process, not the viewer. The first three stages are conditional: with no corpus uploaded and the gate unchecked, a run is just train.

Run

Leave the corpus empty to train on whatever is already prepared in data/tokens. Uploading a .txt re-runs the pipeline from that file (16 MB cap, which is a memory guard: the upload is read into memory whole). Learning a BPE vocab is the slow part, but it scales with distinct words rather than bytes — a 3.5 MB novel collection takes about two minutes, with merge progress and an ETA in the raw log. The overfit gate trains one batch to near-zero loss before the real run starts; if it fails, nothing else runs.

preset
Model size. tiny is 6 layers at d_model 256 over a 256-token context; small is 8 layers at 512 over 512. Both use a 4096-token vocabulary.
steps
Optimiser updates, not passes over the corpus. One step is one batch — 32 × 256 = 8,192 tokens on tiny.
overfit gate
Trains one fixed batch over and over. A model that cannot drive loss to near zero on a single batch is broken, so this catches wiring bugs in seconds instead of after a full run.
BPE vocab
Byte-pair encoding: the token table, built by repeatedly merging the most frequent adjacent pair in a corpus. Training a new one overwrites vocab.json in place, which orphans every checkpoint made before it.
idle — gate: not run corpus: existing tokens

Loss

The dashed line is ln(vocab_size): the loss of a model that has learned nothing, so everything below it is real learning. When the orange line turns back up while the blue keeps falling, the model has started memorising instead of generalising — the chart marks where that began. On a small corpus it happens early and hard, which makes overfitting something you watch rather than read about.

loss
Cross-entropy in nats: the model's average surprise at the token that actually came next. Lower is better, and ln(vocab_size) is what pure guessing scores.
train
Loss on the batches the model is being updated on right now. The optimiser is pushing this number down directly, so it falls almost by construction — it can keep falling long after the model has stopped learning anything general.
val
Loss on held-out text the model never trains on. This is the honest one. The gap between it and train is the part the model memorised rather than learned.
tok/s
Throughput: training tokens consumed per second. A speed measure, not a quality one.

learning rate
How far the optimiser moves on each step. It warms up from near zero over the first 100 steps, then decays along a cosine to a small floor — large steps early to find the basin, small ones late to settle into it.
grad norm
The size of the whole gradient before clipping. Spikes are unstable steps; a value pinned at the clip threshold means the update is being cut every time; a drift toward zero means learning has stalled.
tokens/sec
The same throughput as tok/s, plotted over the run. A steady line means nothing is throttling or contending for the GPU.

Raw log

Every line the child processes printed, parsed or not, in order. The dashboard should never be the only way to see what happened. Blank lines are kept but collapsed to a sliver, so the run stays readable without editing what it printed.

Next-token lab

One forward pass, one distribution. The pale bar is what the model actually predicted; the solid bar is what survives temperature, top-k and top-p. Struck-out rows are candidates the knobs eliminated outright — showing the cut rather than hiding it is the point. The reshaping runs server-side through the same reshape_logits that generate() uses, not a copy of it in JavaScript.

temperature
Divides the logits before the softmax. Below 1 sharpens the distribution toward the model's favourite token; above 1 flattens it toward a coin flip. At 0 it is pure argmax.
top-k
Keep only the k most likely tokens and renormalise, discarding the long tail however likely it was. Off means no cut.
top-p
Nucleus sampling: keep the smallest set of tokens whose probabilities already sum to p. Unlike top-k it adapts — a confident prediction keeps few candidates, an uncertain one keeps many.

Generate

This is a base model, not an assistant. It was trained only to predict the next token in TinyShakespeare, with no instruction tuning and no chat template, so it continues a prefix in the style of its corpus. Ask it a question and it will not answer one. Text streams in as it is produced, one token at a time — there is no KV cache, so you can watch it slow down as the sequence grows.

Attention

Row i is what token i attended to. The empty upper triangle is the causal mask: a token can never see the future, which is the property that makes next-token training honest. Cell shading is sqrt(weight), for display only — attention is spiky, and on a linear ramp everything but the peak would wash out.

layer
Which transformer block, of the 6 in tiny. Early layers tend to attend locally, to the token just behind; later ones carry longer-range structure.
head
Attention runs as several heads in parallel inside one layer, each with its own slice of d_model and its own view of the sequence. Heads specialise, which is why one can look useless and its neighbour sharp.
